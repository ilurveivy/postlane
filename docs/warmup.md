# 邮箱预热：让新邮箱先「像人一样」发几天

新域名 + 新邮箱直接群发冷邮件，是最快的封号方式。预热（warm-up）的目标不是
「攒积分」，而是让收件方（Gmail / Outlook / Yahoo）在**真实互动**里看见这个发件人
是正常的人：有来有回、有人读、有人从垃圾箱里把它拖回来。

现在 Postlane **只做了「量」的一半**：每个账号按 20 → 30 → 50 → 100 → 200 逐日放开
（见 [发送纪律](sending-policy.md)）。它防的是「一天发 500 封」，防不了
「一天发 20 封但 20 封全进垃圾箱」。预热补的就是后半段。

## 一、预热到底在影响什么

ISP 判一个陌生发件人，看的主要是这些信号（按重要程度）：

| 信号                           | 怎么得到     | 能不能自己造      |
| ------------------------------ | ------------ | ----------------- |
| 收件人有回复                   | 真人对真人   | ✅ 自己的账号互回 |
| 从垃圾箱移回收件箱（not spam） | 真人操作     | ✅ 自己的账号可以 |
| 标记已读 / 加星 / 加进联系人   | 真人操作     | ✅ 可以           |
| 发信量平稳上升而不是突变       | 控制节奏     | ✅ 就是排队       |
| SPF / DKIM / DMARC 通过        | DNS 配置     | ✅ 已体检         |
| 被投诉 / 退信率低              | 少发、发对人 | ✅ 已有           |

前四条都是「互动」，靠自己的几个邮箱**互相**制造，不需要真的去打扰客户。
这就是自有账号互寄预热（self warm-up）。

## 二、两种预热路线，选一个

### 路线 A：自有账号互寄（推荐，Postlane 能做）

把**你自己的 4 个以上邮箱**组成一个池子，每天让它们两两互相发几封信、回信、
把信从垃圾箱拖回收件箱、加星、标记已读。全部在你的账号之间完成：

- 不碰客户，零打扰；
- 不需要第三方服务，不额外花钱；
- **可观测**：冷邮件发出去之前，你就能知道「A 发给 B 的信有没有落进收件箱」——
  这就是最直接的落箱检测。

代价：需要多个（≥4 个，最好 6–10 个）邮箱，且最好来自**不同域名**或至少不同提供方；
全部同域名互寄的效果会打折。

### 路线 B：第三方预热网络（Warmy / Mailreach / Lemwarm 这类）

它们有一批真实的第三方用户池，你的账号和别人的账号互寄。效果比 A 好，
因为收件方看到的是**真正不同的组织**在跟你往来。代价是：

- 付费（通常按邮箱数/月）；
- 要把邮箱的 IMAP/SMTP 授权给对方（等于把邮箱交给第三方）；
- 自托管产品没法内置这种网络 —— 它本质是一项**服务**，不是一个开关。

> 结论：Postlane 应该做 A，并且把 B 的接口留出来（外部预热服务通常也会顺带
> 打开「自动化」开关，只要不同时发送即可）。不建议自己实现 B。

## 三、路线 A 具体怎么做

### 3.1 账号池

```yaml
预热池: warmup-pool
  成员:
    - a@yourdomain-a.com   # 主角：即将用来发冷邮件的账号
    - b@yourdomain-a.com
    - c@yourdomain-b.com   # 最好换一个域名
    - d@gmail.com          # 真实 gmail 效果最好（你已经在用的那个）
  每日: 每个成员发出 3–6 封预热信，收到 3–6 封
  时段: 09:00–21:00 新加坡时间随机分钟，不要整点
```

规则：

- **同一对账号不要连续两天互寄**，轮换配对（4 个账号有 12 个有序配对，够转 6 天）；
- 每天的总量随预热阶段递增（见 3.4），不要第一天就拉满；
- 预热信**不占冷邮件额度**（它们不打扰陌生人），但**要算进账号当天总发信量**，
  因为 ISP 看的是总量曲线。

### 3.2 每封信的动作序列

一条完整的「无痕对话」，全程无营销词、无链接、无图片、无签名档：

```
Day 0  10:12  A → B   subject: "那个表格你还有吗"
                    body:  两句话，问一个具体小事（不提产品、不放链接）
Day 0  11:40  B → A   subject: Re: 同样的主题（走 In-Reply-To 同会话）
                    body:  两三句回答
Day 0  14:05  A → B   Re:   一句「收到，谢谢」
Day 0  15:20  B       把 A 的邮件标记已读 + 加星
Day 1  19:30  B       如果发现 A 的信在垃圾箱：移动回收件箱 + 报告「非垃圾邮件」
```

内容从一个**中性话题库**里随机取（日程、文件、发票、会议时间、某个工具的用法……），
每个话题有 3–5 个变体，避免所有账号发出同样的措辞被指纹识别。

### 3.3 落箱检测（这才是真正的价值）

每次 A → B 之后 3 分钟，用 B 的 IMAP 查这封信落在哪个文件夹：

| 结果               | 含义       | 该做什么                                |
| ------------------ | ---------- | --------------------------------------- |
| 在 `INBOX` 且未读  | 正常       | 继续，可以逐步加量                      |
| 在 `Junk` / `Spam` | 信誉还不够 | **把冷邮件额度压回去**，继续预热 3–5 天 |
| 根本没到           | 投递被拒   | 停下查 SPF/DKIM、域名黑名单             |

把「最近 20 封预热信的收件箱命中率」做成一个数字挂在设置页：

```
warmup: 19/20 进收件箱（95%）· 今日额度 100/天 · 建议：可继续加量
```

**连续性判断**：命中率 < 90% 时自动把当日冷邮件额度降到 20，直到连续 3 天 ≥ 95%。
这条比任何「信誉分」都可靠，因为它是你自己发出去、自己收的，不依赖第三方。

### 3.4 日历（以 4 个账号为例）

| 阶段   | 天    | 每个账号每天预热信 | 每个账号每天冷邮件上限 | 备注                               |
| ------ | ----- | ------------------ | ---------------------- | ---------------------------------- |
| 只预热 | 1–3   | 3                  | **0**                  | 把池子跑起来，看落箱               |
| 只预热 | 4–7   | 5                  | **0**                  | 出现垃圾箱就继续停留               |
| 混合   | 8–14  | 6                  | 10–20                  | 冷邮件一天最多一轮，跟进也在这轮里 |
| 混合   | 15–21 | 6                  | 30–50                  | 命中率 ≥ 95% 才加量                |
| 常规   | 22+   | 3（维持）          | 按 ramp 走 50→100→200  | 预热不要停，它是体检               |

第一封冷邮件之前**至少 7 天纯预热**。这个数字不是玄学：新域名的 DNS 与 IP
声誉在前一周最脆弱，而这一周的预热成本几乎为零。

## 四、放进 Postlane 的产品形态

```
设置 → 预热
  预热池：勾选参与互寄的账号（至少 2 个）
  每日强度：3 / 5 / 6 封
  时段：跟随发送时段 / 单独设置
  开关：暂停预热 / 只预热（暂停所有冷邮件）
状态卡：
  今日已互寄 12 封 · 落箱 11/12 · 冷邮件额度 20/天（因预热期受限）
  最近 7 天落箱率：96%（建议加量）
```

实现上不需要新机制，都能复用现有零件：

- 发信：`mailer` 现有的 SMTP 通道 + 队列（预热任务只是一个特殊 campaign，
  `mode: 'warmup'`，不进报表、不占批次）；
- 收信：`followup` 的 IMAP 通道（`imapflow`）读指定文件夹，判断消息落在 INBOX 还是 Junk；
- 落箱率：存 `warmup-evidence`（messageId / 文件夹 / 时间），算最近 N 封的命中率；
- 联动：`dailyCapFor()` 读落箱率，低于阈值时把上限压到 20（而不是只靠账号年龄）；
- 数据模型：`warmup-pool`、`warmup-thread`（配对 + 话题 + 状态机）、`warmup-evidence`。

需要注意的三件事：

1. **不要把预热信发进任何真实名单**，也别让它出现在报表/批次里，否则统计会被污染；
2. **不要在预热和冷邮件之间复用同一段文案**，指纹会串；
3. 预热要**跨域名**：自己一个域名互寄，效果远不如「域名 A ↔ gmail」。
   如果只有一个域名，先把 gmail/outlook 的个人邮箱放进池子。

## 五、没有预热引擎时，现在可以怎么做

在预热功能上线前，最省事的替代是**手动跑两周**：

```bash
# 用一个小批次、间隔 1 天验证跟进节奏（见 followups.md 的自查段）
# 然后人工：每天给自己另一个邮箱发 3–5 封普通邮件，互相回复，
# 检查 Gmail 里它们是落在收件箱还是垃圾箱 —— 这就是最原始的预热。
```

同时把冷邮件额度**手动压住**：现在 ramp 是自动的，第 1 天就有 20 封，
如果落箱没确认，这 20 封就是在拿域名赌。

## 六、要不要现在做

预热引擎大致分两块，可以分开上：

| 块      | 内容                                                     | 大致工作量                                                 |
| ------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| A1 观测 | 预热池配置 + 每日互寄 + 落箱检测 + 落箱率面板 + 额度联动 | 一次完整的实现（约 1 个新模块 + IMAP 文件夹判定 + 设置页） |
| A2 拟真 | 话题库、配对轮换、加星/标记已读/移出垃圾箱、随机分钟     | 在 A1 上加一层动作脚本                                     |

建议先上 A1 —— 它已经能回答最重要的问题：「我的信到底进不进收件箱」。
A2 是锦上添花，可以在拥有稳定池子之后再加。
